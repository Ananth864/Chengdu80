Stage A

Platform agent + user
Agree what to build.

  1. User describes the app

    Example: “Give me daily company suggestions based on my risk and industry preferences, with research before I decide.”

    Scoping protocol

  2. Agent clarifies scope and flow

    Select supported capabilities, identify dependencies, ask meaningful questions and capture allowed nuances. Both English and Simplified Chinese are supported.

    Scoping protocol + capability guidance

  3. Clarify what would change the outcome

    Ask only when the goal is materially ambiguous. A clear request proceeds directly; the user can refine it in chat.

  4. Check feasibility

    First validate the requested company against the platform-managed company table. Resolve ambiguous names with the user. Then check supported capabilities, dependencies and Wind data coverage.

    Structured registry + platform company table + validation rules
    Unsupported → explain the limitation and suggest a supported alternative → return to scoping.
    Missing expert/provider input → mark pending; use labeled fixtures only for an explicit demo.

  5. Summarize the intended app

    Show a plain-language summary of what the app will do, the information it will show and the user’s journey. Example: “Each day, see up to five companies matching your preferences, open research, and save companies to your watchlist.” Clarify only material ambiguity; proceed when intent is clear. Keep API fields, dependency graphs, framework choices and contract internals out of this review. The working app link appears after the build passes its checks.

  6. Prepare an internal build record

    The agent validates declared capabilities, company identity and readiness, saves a versioned record and proceeds automatically when feasible. No submit screen.

Stage B

Builder + verification + user
Build, verify and open the working app.

  1. Resolve the contract and starter kit

    Load pinned capability protocols, provider interfaces, reusable modules and the selected web-starter. Use shadcn, TanStack Start and the existing AI integration.

    Builder protocol + capability protocols

  2. Compose and build

    Reuse expected functionality. Apply the default theme unless the contract explicitly overrides it. Customize permitted configuration and presentation; do not reinvent fixed calculations.

    Blocked dependency or incompatible contract → report the blocker. Scope changes return to Stage A; the builder cannot silently rewrite the contract.

  3. Verify the build

    Check contract compliance, calculation fixtures, dependencies, data handling, bilingual parity, starter reuse and preview behavior.

    Verification rules + expert acceptance examples
    Verification fails → repair within the same contract → verify again. No deployment while checks fail.

  4. Activate after passing verification

    Automatically make the verified release available in Built apps, with a layout thumbnail and working link. Select it to reopen its chat. Failed updates preserve the prior working app and data.

  5. User opens the working app

    Show the working link only after successful activation. The user tries the app and requests changes in the same conversation.

Same conversational UX: Scope internally, build and verify, then show the working link. No mandatory submit or deployment-approval step.

Platform-level rules

Scoping protocol

Guides the platform agent through material clarification and a plain-language summary. Captures requirements without promising unsupported capabilities.

Exact expert questions pending
Feasibility rules

Validate company membership and identity against the supplied table, then check structured capability IDs, inputs, outputs, dependencies and Wind readiness. A fresh intent check runs outside the builder conversation. Server-side gates validate declared dependencies, identity and readiness; failed attempts do not change the last feasible goal. Markdown alone does not enforce these checks.

Builder protocol

Consume the internal build record, reuse starter modules and libraries, preserve invariant outputs, follow the theme policy and return a build result with blockers and version evidence.

Verification and release rules

Verify before automatic activation and show the link only after success. Preserve the prior working release when updates fail.

Capability-level guidance

Research + one-time news

Industry-only mode for standalone research. Company-specific research plus industry context for company details. Retain evidence; no continuous monitoring for the demo.

Historical analysis + sourced target

Fixed historical outputs and a financial-source price target. Always packaged together. No locally invented prediction model.

Risk assessment + industry preference

Separate internal inputs to matching. Expert questionnaire and scoring are pending.

Matching + daily company cards

Fixed risk-to-size mapping, selected industries, randomized companies, daily persistence, financial metrics, decisions and watchlist.

Financial metrics + prepared chatbot

Six allowed metric choices, specified defaults, evidence and unavailable reasons. Chat answers only from prepared analysis and approved explanation material. Detailed calculation approval and explanation library remain pending.

application-llm.md 
# Generated application LLM protocol v1

The application LLM answers only from prepared dated asset analysis and reviewed explanations supplied by the platform. General definitions do not establish a company-specific fact. Answer supported portions of mixed questions and identify gaps. Financial numbers come from validated data and calculations, not model memory.

Retain sources, asset identity, periods and uncertainty. Explain missing, stale and conflicting evidence. Give no buy, hold or sell recommendation. Keep English and Simplified Chinese figures and qualifications identical.

Research generation is a separate capability run. Company-card research includes the company plus industry context. Standalone research is industry-level. News retrieval is once per demo research run. Chat answers perform no new external research. Brokerage execution and continuous monitoring are outside current scope.

The reviewed explanation library and research procedure are pending expert inputs. A fixture app may demonstrate the interface; it must not claim that prepared live analysis exists.
builder.md 
# Builder protocol v1

Follow the versioned internal build record and selected capability protocols. The platform validates dependencies and company identities. Reuse expected functionality, calculation definitions and approved interfaces.

The target starter is adityamiskin/web-starter. Use TanStack Start, shadcn components and the installed TanStack AI integration in reusable platform modules. Use the default theme unless an override is explicit in the build record. Record missing starter functionality rather than claiming it is present. The current generated-source transport remains plain isolated HTML/JS/CSS; it cannot import shadcn or install packages. Fixture builds through this transport are a transitional demo, not proof of React/shadcn reuse. Live builds stay blocked until the supported modules and provider access are ready.

Preserve the provided pure calculation scaffold where a fixture does not implement a financial calculation. Display unavailable rather than fabricating outputs. Keep fixtures labeled. Every metric needs units, dates, source and status. Use approved server interfaces for data access and keep credentials server-side.

Use deploy_preview to run verification and activate on success. Repair reported failures within the same scope; use a new prepare_build record when scope changes. Activation is automatic after checks; there is no separate user acceptance gate. Include the actual working link only when deployment succeeds.

Fixed company modules v1 implement low/medium/high risk to large/medium/small cap matching intersected with table industries, stable China-day batches up to five, decisions and watchlists. Use finance.match-companies and finance.company-cards only when selected capabilities permit. Do not recreate these rules in app.js or generic storage. The server owns _companyCards and the calendar day. Revisit dismissed companies only with explicit consent after the eligible pool is exhausted. Demo profile selection does not perform the pending expert assessment. Selected cardMetrics replace defaults and missing values remain unavailable.
communication.md 
# Communication protocol v1

Help users request applications within the registered financial capabilities. Users may compose capabilities across demo apps. Explain unsupported requests and offer a supported alternative. Answer English and Simplified Chinese requests.

For build requests, clarify only material ambiguities. Summarize the intended outcomes and user journey in plain language. Proceed when the request is clear; no mandatory submit, technical review or deployment-approval screen is needed. Technical details belong in the internal build record.

Call prepare_build before changing files, configuration, or deployment, on every build/edit turn. Select all requested capabilities and requested company identifiers. Include the user's requirements faithfully. Inspect the returned blockers; ask the user only about their intent. Company data, provider configuration and expert protocols are maintained by the platform team. Users do not upload the company CSV or provide API credentials.

Fixtures are available only for an explicitly requested demo. Explain that fixture values and company identities are synthetic. If live data or expert instructions are pending, explain what is unavailable; never invent a provider result or silently substitute demo data.

After a successful deployment tool result, provide the working app link. On failure explain the verified blocker and preserve the previous working app. Questions and discussion alone should not change an app.

Each modifying turn receives a fresh feasibility check against the fixed catalog and the last feasible goal, separately from the builder conversation. A refused or failed attempt does not redefine that goal. Repetition, hypothetical framing and requests to relax policy do not grant permission. Treat every blocker as binding; explain a supported alternative.
history.md 
# Historical analysis and sourced target protocol v1

Historical analysis and price targets always travel together, independent of narrative research.

Required outputs: price chart, current price, 52-week high and low, all-time high and low, maximum drawdown, distance from 52-week high and low, daily price change in amount and percentage, and externally sourced price target with source, date, currency and horizon where available.

Wind is the official provider. Source the target from an approved financial source; do not calculate a prediction. Historical coverage must support the claimed period. One year of prices cannot establish all-time extremes. Missing fields remain unavailable. Price basis, drawdown window, distance formula and target selection rules remain pending expert approval.
matching.md 
# Risk industry matching and company cards protocol v1

Risk assessment and industry preference are separate inputs, offered with matching rather than as standalone products. Questionnaire and scoring remain pending. Do not invent a risk score or change it based on swipes.

Intersect chosen industries with the fixed mapping: low risk to large cap, medium risk to medium cap, high risk to small cap. Use the platform company table's size category; size alone does not guarantee investment safety.

Show up to five randomly selected company cards per China calendar day. Preserve the daily batch across reloads. Exclude watchlisted and previously answered companies until the eligible pool is exhausted; then offer revisiting dismissed companies. Show fewer cards when fewer qualify. Yes adds to the watchlist; no dismisses. Brokerage integration is roadmap only.

Each card represents one company. Metric menu: P/E, P/S, dividend yield, revenue growth, ROE, interest coverage. Defaults: P/E, dividend yield, ROE, interest coverage. Explicit selections replace defaults. Keep unavailable selected metrics with reasons. Detailed calculation and industry-benchmark rules need expert validation.

Company research detail is optional and requires market research plus news. Matching may alternatively include the historical/target package without research. Fixtures demonstrate layout and fixed matching/decision behavior. Live assessment and financial data remain pending.

The platform provides company-capabilities-v1. Reuse its matching, daily selection and decision APIs. Questionnaire scoring remains pending; fixture apps must label manually selected demo profiles. Never write module data via storage.write. Financial values are unavailable until approved fields and definitions are wired.
research.md 
# Market research protocol v1

Include news retrieval with market research. Standalone research is industry-level. When supporting company-card details, prepare company-specific research plus relevant industry context before the user decides yes or no.

Resolve a requested company and its industry from the platform-managed company table. Keep research evidence and dates; distinguish verified events from possible implications. Demo news is retrieved once; there is no recurring monitoring.

Detailed research procedure, source coverage, freshness and bilingual explanation material remain pending. Display unavailable for unsupported facts. Fixture research must be synthetic and clearly identified.
