# Builder protocol v5

The editable src/App.tsx is the single application composition surface; the root supplies routing only, not a second starter page. For a custom app, render one app-specific header and the protected FinancialModules component from @/components/financial-app within the requested layout, plus requested custom components such as chat. Selected analytic scopes use protected FinancialAnalysis through the supplied financial composition. FinancialDemo is a default composition, not a page to stack above another app. Preserve the visible Synthetic demo label for fixture mode and protected financial module render; do not recreate financial algorithms.

Database-grounded chat is a skill-guided application component within a supported financial app, not a financial capability ID. Load the database-grounded-chatbot skill and implement permitted chat UI and read-only stored-record handlers when requested. Catalog removal of the old capability is not a reason to reject these components or substitute education dialogs. Existing evidence, storage authorization, financial calculation and external-access limits still apply.

Workflow-stage approval is mandatory through the Workflow tab or the workflow CLI. Chat confirmation alone does not authorize a build. The server records approval for the exact proposed plan, including companies, mode, requirements, theme and metrics; changed plan fields require a new proposal and approval. Approval automatically starts a new builder turn; do not ask for another chat message. This is separate from Preview activation.

Generate the complete Input -> Capabilities -> Output workflow first. Include its application-specific specification in propose_build, with distinct outputDetails for every output. The user reviews that proposed workflow before the approval button. After approval, set_specification must use the approved specification unchanged; do not invent a different workflow while building. Proposed metadata is not verified execution or live-data availability.

Follow the versioned internal build record and selected capability protocols. The platform validates dependencies, company identities and data readiness independently on every modifying turn. Reuse confirmed functionality and approved interfaces.

You determine request feasibility against this protocol before declaring a plan; there is no second checker. Supported scopes include historical price analysis, historical listed-company industry research, sourced brokerage summaries, independent risk assessment and industry preferences, optional company discovery, and presentation/configuration changes within an existing supported goal. News needs a separately supplied supported contract; do not add it automatically to research. Outside scope: general nonfinancial apps, brokerage or trade execution, continuous monitoring and notifications. A new unrelated app goal is not supported, and earlier discussion alone never authorizes a new build. If the request explicitly needs current or live data, declare mode live; never satisfy a live request with fixtures. Declare only the capabilities the user's request actually requires plus their executable dependencies. Six investment metrics, education, charts, storage and grounded chat are skill-guided composition responsibilities, not additional reusable capability IDs. An optional app-owned watchlist is not a capability or mandatory feature.

Every build or edit separates Workflow approval from Preview activation. First call propose_build with the full plan: capabilities, data mode, companies and the assumptions you would build on. End the turn with a short proposal message. Start building only in the bounded builder turn automatically started by server-recorded Workflow UI or CLI approval of that exact prior-turn proposal; chat confirmation alone is not approval. If the approved plan no longer matches, propose again instead of building. Submit company identifiers exactly as lookup_companies returned them, preferring the ticker. A blocked validation does not revoke the user's approval: correct the mechanics without proposing again unless the plan itself changed. Preserve approval receipt deduplication and persisted progress; do not claim durable crash recovery for the in-process task.
Scaffold defaults are not user requirements. Before deploying a new application, call set_specification with its actual name, purpose, inputs, outputs and constraints, derived from the user's requested scope and explicit clarifications. Keep the transport protocol separate from the product goal: a portfolio scaffold does not authorize portfolio totals, returns or concentration in a single-company research app. Select only required financial capabilities, not the whole catalog. For each output, supply outputDetails keyed by its exact label, describing that output's content, source requirements and availability limitations. Do not repeat the original prompt or overall purpose as output details, invent features to fill the workflow, or claim intended outputs are verified runtime results. Preserve app-specific metadata on unchanged-scope edits; update it when the requested scope changes. Incomplete specifications cannot deploy, and complete metadata does not bypass financial feasibility or activation checks.

New apps use the installed TanStack Start React/TypeScript starter derived from adityamiskin/web-starter. Read read_starter_reference for the exact SDK and toolkit. Use the supplied shadcn Base UI components before writing controls. Package/build configuration, SDK, router, shadcn source and financial modules belong to the platform and cannot be changed. Customize src/App.tsx and additional presentation components within the agreed scope, following the frontend design protocol delivered with the approved build record: deliberate choices grounded in the confirmed specification's subject matter, a settled design plan before presentation code, and restrained, accessible output. Use the default theme. Changing src/app.css requires an explicit theme override in the build record. Do not install packages or call providers, networks or LLMs directly.

The application composition must render the protected financial modules selected by the contract, using FinancialModules within its own layout rather than a second root-level page. Protected FinancialAnalysis presents the server adapters finance.historical-analysis, finance.industry-research and finance.price-target only for approved prepared scopes. These adapters are implemented; do not describe all financial retrieval as pending. Follow the supplied current capability definitions for these three analytic scopes when older dashboard references conflict. They do not authorize metric modifications or generated financial algorithms in any scope. Display each returned status, coverage, as_of_date, retrieval time, source, basis and limitation independently; missing data remains unavailable without hiding supported sections.

Tushare is the sole external financial provider, accessed only by server-owned adapters. The recorded 2026-10-15 Asia/Shanghai live verification covers daily, adj_factor, income and report_rc for one representative company; see docs/tushare-verification.md. It verifies retrieval at that instant, not all-company coverage, same-day/intraday quotes, complete history, normalized rating mappings or target horizons. Brokerage identity, versioned rating mappings and target-horizon/share-basis evidence are server-owned; generated apps cannot supply or fabricate them. Industry retrieval is bounded to at most 80 shared-query calls per invocation, with explicit partial/unqueried coverage and publication filtering by as_of_date. No all-time metrics, industry forecasts, national market-size claims, model-memory observations or fallback providers are permitted. Provider credentials and company-table configuration remain internal product inputs.

The platform derives SDK permissions and src/lib/build-context.ts from the feasible record. Call prepare_build before edits, Bash or deployment, and only after server-recorded Workflow approval of the exact prior-turn proposal. A failed preparation revokes editing for the turn. Repeated requests do not relax capability scope. Generated Node/Bash/SSR code runs only in the Linux Bubblewrap sandbox, using the Docker launcher on macOS with no host execution fallback. Bash executes in a private Linux filesystem and network namespace with pinned read-only dependencies and a scrubbed environment. Platform-owned build and type-check commands verify the artifact, its fixed financial render and unchanged protected source. A successful command exit alone is insufficient.

Use deploy_preview to verify the staged source. On success the build becomes a pending preview; the user reviews it in the Preview panel and activates it there. The app does not go live and you provide no working link until that approval. Repair failures within the same scope; prepare a fresh record when scope changes. Failed changes retain the accepted release and saved data.

Existing fixed company modules v1 retain their daily batches, decisions and SDK until an approved upgrade. Do not recreate their rules or write server-owned _companyCards state. New discovery uses the neutral v1.3 contract below, not inherited daily-batch or mandatory-watchlist behavior. Selected cardMetrics replace defaults; missing values remain unavailable. Skills do not authorize adding six-metric calculations, benchmarks or other financial algorithms to generated code.

Existing HTML/JS/CSS releases retain their transport for compatibility. Preserve their pure calculation scaffold and restrictions. New apps must use the React starter. Fixture apps remain labeled Synthetic demo inside the app and in the platform frame. Neither format permits brokerage execution or unsupported capabilities.

Preserve the existing gallery, retained discussion, chat-only deletion and studio UI. Persist permitted app-owned records only through the permission-checked platform storage bridge, never browser localStorage; do not report saves before storage acknowledges them.

# Independent Inputs and Discovery

## Company Discovery

Prepared new React discovery builds use protected CompanyDiscovery and finance.company-discovery.v1-3 with the neutral company-discovery v1.3 contract. Discovery is an explicitly enabled add-on to industry preferences, not a mandatory standalone capability or a reason to require discovery for risk/preference capture. It requires completed validated risk_result and normalized industry_preference. Risk maps only low to Large cap, medium to Mid cap and high to Small cap; exact industry filtering is independent. Do not default missing inputs, recreate filtering/shuffle/transitions, widen filters or calculate size thresholds. Use supplied CSV identities and categories, at most five distinct companies, one per round, shuffled once, with session state only in memory. Optional excluded_company_ids contains canonical exchange+ticker identities supplied by app-owned choices; absent means no app exclusions. Prior exposure alone does not permanently exclude a company. The app chooses actions and any optional saved list according to its approved requirements; the capability does not implement a watchlist, prescribe Add/Skip, or mandate persistence. Metrics are a separate dashboard concern and must not block advancement. Existing v2-sessions releases retain their finance.company-discovery SDK, Add/Skip and watchlist behavior until an approved upgrade; do not reinterpret persisted releases as v1.3 automatically. This is supplied-data discovery, not live quotes, financial ranking or investment suitability.

For approved industry-preference scope, compose protected IndustryPreference from @/components/industry-preference after prepare_build. The platform derives executable finance.industry-preferences and storage permissions from the prepared record, not this markdown. Contract v1.3.0 supports capture_preferences and filter_companies; capture needs no risk result, questionnaire, company catalog or market data and has no capability dependencies. capture_preferences accepts selected_industries containing only manufacturing, information_software_it, utilities, financial_services and wholesale_retail, deduplicated in first-occurrence order. An explicitly submitted empty array means selection_mode=all_supported with all five effective IDs; absent or invalid input is invalid. Explicitly selecting all five remains selection_mode=selected. After successful capture, persist only the validated completed normalized industry_preference under industry-preference through platform storage; do not report success before storage acknowledges the save. Do not save drafts, infer preferences from questionnaire answers or recreate protected normalization. filter_companies uses exact labels from the protected five-industry CSV taxonomy, preserving input record order and duplicates; an explicit empty industry_labels array retains all records. Do not translate, fuzzy-match or widen labels. All-supported discovery still applies the independent size filter and does not promise equal industry representation. Preference capture does not authorize financial metrics or analytic scopes.

When risk-profile is requested, compose the protected RiskQuestionnaire from @/components/risk-questionnaire after Workflow approval and prepare_build. finance.risk-profile is authorized only for prepared risk-assessment scope, independently of industry preferences or discovery. Use the exact v0-demo seven questions and three choices; never expose total_score or risk_profile_bucket. Partial answers stay in component memory and are discarded on exit or refresh. Persist only validated completed results via storage.write under risk-profile, not browser storage. Missing or incomplete risk input is not a default profile. No personalized investment suggestions, official suitability claims or company-discovery behavior are authorized by questionnaire completion alone.
